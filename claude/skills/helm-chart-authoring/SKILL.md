# Helm chart authoring

Write templates the reader can follow top to bottom. Explicit duplication beats a clever `range` over `list` with a group index; never trade readability for fewer lines. Use few named helpers: add one only for a real gain (logic reused in several templates, or a rule that must stay identical everywhere), never to shorten a template; inline a snippet used once or twice, and keep `_helpers.tpl` to the standard `helm create` helpers unless the user asks for more. Avoid upfront variables (`{{- $x := … }}` blocks at the top of a template): write the expression where it is used, so the reader does not jump back. Read nested map values with `dig` and a default, from a map that always exists: `dig "service" "ports" "http" 8080 .Values.AsMap`, or from a `range` entry; in Helm 4 (verified 4.3.1) `dig` on `.Values` itself fails ("common.Values, not map[string]interface {}"), and `dig` on a sub-map that is absent (`.Values.nope`) fails too. When the user asks for a split, each helper covers one responsibility (names, image, container, pod), stays short enough to read top to bottom without scrolling, and needs no comment to be understood; a single 280-line pod helper that the user calls unusable is the failure to avoid. Helm replaces lists on merge, so anything an environment overrides is a map keyed by name (for example a `jobs` map keyed by job name), never a list.

- Object names: `app.name` is `nameOverride`, else `.Release.Name`, never `.Chart.Name`. When the chart is consumed as a dependency under an alias, `.Chart.Name` and `.Chart.Version` are the alias and the dependency version, so any label built from them changes the consumer's render; the consumer's original chart name must survive, or the change is reported and ruled on.
- A chart whose minimal case renders no object still needs a `chart/templates/` directory (a `.gitkeep` is enough): `helm lint --strict` fails without it. Keep both `nameOverride` and `fullnameOverride` with the usual `helm create` logic, even when the release name already gives the right name: they are standard Helm and the user expects them.
- Containers: render `initContainers` in one block, then `sidecars` in a separate block that sets `restartPolicy: Always`. The map key is the container name, and init order is the alphabetical key order; say so in values.yaml and the README. Container names must be unique across `initContainers`, `sidecars` and the main container (Kubernetes rejects duplicates), so a key reused across them fails the render. Init containers and sidecars inherit `global.image.pullPolicy` unless they set their own.
- Pod security: every workload (Deployment, Job, CronJob) renders the restricted defaults on the pod and on each container (main, init, sidecars); the field list, the emptyDir rule and the policy check are in k8s-restricted. Prove the defaults in the render check and in helm-unittest.
- Conflicts: if one key exists in both `initContainers` and `sidecars`, `fail` with a message naming the key. Prove it with a refused case in the render check.
- Schema: set `additionalProperties: false` on each container entry, so a removed key (such as a former `sidecar: true` flag) is refused by name.
- Shared pod schema (hand-written; superseded by the helm-schema bullet at the end of this list): declare the pod block once under `$defs` and extend it for `deployment`, each job and each cronJob with `allOf` plus `unevaluatedProperties: false`. Helm 4 (v4.3.1, checked on a throwaway chart) accepts JSON Schema 2020-12 this way and refuses an unknown key in every object kind. For an invalid value the error points at the parent object, not the key, so keep the refused-case checks per object kind.
- No hidden defaults: an environment-specific value (issuer, secret name, host) is never hard-coded in a template. It is written in the values, and values.yaml comments say what it drives (for example "`tls.issuer` sets the `cert-manager.io/issuer` annotation").
- Per-environment files hold only what really varies by environment (the environment name, a per-environment namespace, a host that depends on the namespace). A key an environment file sets to the same value as `chart/values.yaml` is redundant: delete the line, do not correct it, and drop the parent block when its last key goes. Prove it by rendering every environment before and after with `helm template` into files and comparing them with `cmp`; the renders must be byte-identical.
- When a shared target lives in a namespace that differs per environment, add one per-environment namespace value (for example `authnNamespace` set to the environment's namespace) and build the global host from it in `values.yaml`, such as `hydra-admin.{{ .Values.authnNamespace }}.svc`. Each environment file then sets only the namespace value and does not repeat the host.
- Alias or FQDN URLs in a consumer of shared-chart (strict schema): write them literally. Production values are the default in `chart/values.yaml`, and each environment file overrides with its own literal prefix (`int.`, `staging.`, `preprod.`). Do not add a `dnsPrefix` value, and do not compute a prefix in a template (`has`, `ternary`, `$p`); the user ruled this on 21/10 and the strict schema refuses the extra key anyway.
- Never build a Kubernetes Service name from `.Values.environment` or an environment suffix. Write the literal Service name, and confirm it by listing the namespace's Services (see readonly-cluster-and-secret-inspection) before committing it to a value.
- Service URLs in `env` are literal and short: a service in the same namespace is written with its bare Service name (`http://hydra-admin`), with no namespace, no `.svc` suffix and no environment segment. Do not run `env` values through `tpl`; the user rejected that on 2026-10-19. The bare name only resolves when the release name carries no environment suffix, so until release names are constant, consuming values write the real suffixed name and say so.
- Derived annotations yield to explicit ones: set a derived annotation only when `annotations` lacks that key (`hasKey`), so the rendered object never carries the same key twice.
- One TLS shape: `tls: {secretName, issuer}` on `ingress` and on each `extraIngresses` entry, with `required` on `secretName`.
- Job and CronJob pods must never be selected by a Service. A Service selects on the Deployment's labels, and a running Job pod without a readiness probe counts as ready, so give job pods a `name` label distinct from the Deployment's (app name joined with the job key by a dash). The same selector drives NetworkPolicies, so they stop covering job pods; a job that needs network access gets its own policy. Fail the render when that label exceeds 63 characters instead of truncating it.
- Several objects of one kind (ConfigMap, ExternalSecret) are a map keyed by name, never a single object or a list, and the map key sets the object name suffix. Each entry takes `enabled` (absent means on), an optional `name` to force the object name, and an `annotations` map. Every rendered object takes `annotations`, so Helm hook annotations such as `helm.sh/hook` can be set on a Job. Decide these before the first published tag: after it, the change breaks consumers.
- Images: `global.image` gives the default `pullPolicy` and either a `tag` or a `digest`; the schema accepts a digest only as `sha256:` followed by 64 hex characters. A container with neither fails the render and names itself.
- Prove each claimed behaviour (override wins, refusal, order) with a case in the render check, not with a claim. See helm-render-diff-check.
- Never read a value that may be `0`, `false` or `""` with `| default N`: `default` replaces it, so `replicas: 0` renders as `1` and an environment cannot be scaled to zero. Use `dig "key" fallback $map` or test `hasKey`, and render a `0` / `false` case in the check. Replacing `default` by `dig` also changes `""`: `dig` keeps an explicit empty string that `default` used to replace, so keep `default` where `""` means unset (an empty name or containerName), and check each key whose behaviour changes in the render diff. Read nested optional keys with `dig` and let the fallback be a variable, for example `$globalRepo := .Values.global.image.repository` then `dig "image" "repository" $globalRepo $container`, so each container's own value wins and the default stays readable.
- The `hasKey` annotation rule applies to every object that merges annotations (extra Ingresses and router middlewares included), not only the main Ingress. Build the derived annotations with `dict`, merge the explicit ones over them, and render with `toYaml`, so no key appears twice; then check one explicit override per derived key.
- A refused-case check greps the expected `fail` message, not only a non-zero exit, so an unrelated error cannot pass for the refusal.
- A chart option the smoke case never sets (a middleware, a conditional ingress field) is untested: add it to the smoke values when the chart ships it.
- When migrating a chart, render an optional field only when it is written (for example `replicas` only when `deployment.replicas` is set), so the minimal case matches the previous chart's output.
- The shipped values.yaml must pass the schema as written: every placeholder in it is validated, so an empty enum value such as `type: ""` (schema enum `kubernetes`/`cilium`) breaks `helm template -f values.yaml`. Comment such a line out (`# type: kubernetes`) and let the comment document the default.
- The render check must include the minimal case rendered with the documented values.yaml, not only with `{}`. Rendering with `{}` hides every schema refusal in the shipped file.
- Templates must render the minimal case the same with or without values.yaml defaults. When a default changes (for example `service.enabled` going from `true` to absent = disabled), state it in values.yaml and in the render check, because consumers that relied on the old default silently lose the object in their render diff.
- Helm library chart (`type: library`) shared by consuming charts: the library's `values.schema.json` is not enforced on the consuming chart's values, so an unknown key passes. Copy the schema into each consuming chart and add `"<library-key>": {"type": "object"}` to its properties; without that entry every render fails with `additional properties '<library-key>' not allowed`. `.Chart.Name` in labels is the consuming chart's name, and the library version appears in no label. Prove a refused key in the consuming chart, not in the library. Observed on Helm 4.3.0 in a pilot.
- Flux HelmChart whose chart is a `file://` dependency outside the GitRepository root: source-controller confines the path to the repo root (read from its source, not tested). A private Helm dependency needs a HelmRepository and a credentials Secret in each namespace, otherwise the download is anonymous. A committed `charts/*.tgz` of that dependency sidesteps the HelmRepository; see shared-chart-consumption for the shared-chart case.
- Schema source: `values.schema.json` is generated by `helm-schema` from `@schema` annotations written in values.yaml, never hand-edited. A pre-commit hook regenerates it so a commit never carries a stale schema. The user required this on 2026-10-19: the schema comes from helm-schema, values.yaml is annotated properly, and a pre-commit hook regenerates it. Helm-schema 0.23.5 (`aqua:dadav/helm-schema`) is the version the sibling deployment repos pin; its `--check` (`-C`) exits non-zero when a schema is missing or stale, so the hook runs it, and `--uncomment` (`-u`) reads commented-out keys. helm-schema 0.23.5 emits draft-07 with `definitions`, not `$defs`, so `unevaluatedProperties` is unavailable and the shared pod block cannot rely on it. Each refused case must be re-proven against the message helm-schema emits (`additional properties '...' not allowed`), and any refusal it cannot express is listed, not dropped. Regenerating the schema can tighten fields silently (init and sidecar `env` became the same definition as the main container's): diff the minimal-case render after each regeneration, and put the annotations in values.yaml, never in the generated file.
- Before reporting "nothing to regenerate" after a values.yaml change, check whether the repo tracks `values.schema.json` and `HELM.md`: `git ls-tree -r --name-only origin/<base> | grep -E 'values.schema.json|HELM.md'`. Repos of the same chart family differ: some ship both, others neither. When they exist, regenerate with the repo's tasks (`mise run schema:helm`, `mise run docs:helm`) and commit the generated files in the same commit as the values change. Default-value changes touch these generated files in every MR that edits values.yaml, so sibling MRs conflict on them: the MR merged second is rebased and regenerated with the same tasks, never hand-merged. List the files each MR touches (`glab api projects/<id>/merge_requests/<iid>/changes`) to find the overlap before the batch is handed over.
- After a resource value change, render each environment the HelmRelease lists in `spec.chart.spec.valuesFiles` with `helm template <release> chart -f values.yaml -f <env>.yaml | grep <key>` and quote the rendered value per container, init containers included.
- Non-sensitive settings (internal service URLs, e-mail addresses, domains, partner labels) go in a ConfigMap, never a Secret, and no ExternalSecret is added for them. A Secret or ExternalSecret is for real credentials only. The user asked why a Secret was used and chose the ConfigMap on 2026-10-19.
- A PVC name shared by two releases in one namespace cannot be created by both: Helm stamps `meta.helm.sh/release-name` on each object, so the second release fails. Only one release declares the claim; the other mounts it by name.
- Every container kind takes the same field set: main container, init containers, sidecars, Jobs and CronJobs all accept `envFrom` (configMap or secret reference, optional prefix). When adding a container field, check it on each kind.
- Optional top-level objects (Service, Ingress, NetworkPolicy, Role) render only when their key is set, so the minimal case renders none of them. Say so in values.yaml, and make the default change visible in the render diff.
- A ConfigMap `files` entry is a YAML block scalar (`|`). YAML infers the block's indentation from its first line, so a first line indented more than the rest fails the render with `YAML parse error`. Write the header with an explicit indentation indicator (`|2`, relative to the key's own indentation) and prove it with a case whose first line starts with spaces.
- YAML 1.1 reads bare `n`, `y`, `on` and `off` as booleans, both as keys and as values. Rename them in values.yaml and in the smoke cases.
- Go template `if` and `with` treat `false` and `0` as absent, so `automount: false` or `terminationGracePeriodSeconds: 0` silently disappear. Test `hasKey` for such booleans and numbers, and render the `false` and `0` cases in the check.
- A switchable variant of one object (standard NetworkPolicy or Cilium) is one key with a `type` enum; both variants come from the same key, and each variant gets its own refused-case check.
- Restart on ConfigMap change: the Deployment pod template carries `checksum/config`, the sha256 of the rendered ConfigMap template (`include (print $.Template.BasePath "/configmap.yaml") . | sha256sum`), set only when the chart renders at least one ConfigMap. Opt out with `deployment.restartOnConfigChange: false`; an explicit `checksum/config` in `podAnnotations` wins. Never put it on Job pod templates (`spec.template` is immutable, so `helm upgrade` fails on an existing Job) or on CronJobs (each run reads the current config). The checksum covers every ConfigMap the chart renders, not only the ones the pod mounts; say so in the README. Prove it in the check: present with ConfigMaps, changed by a ConfigMap value, unchanged by an unrelated value such as a service port, absent without ConfigMap, absent on Job and CronJob, and an explicit annotation wins.

- Several releases of one chart repository share one set of values. The GitOps HelmRelease passes only the repo's `values.yaml` and `<env>.yaml` (`chart.spec.valuesFiles`), with no per-release values block, so releases of the same repo render identical values. A per-release difference must be derived from `.Release.Name`, or the release must live in its own repo. Read the HelmRelease template before proposing a per-release option in a shared chart.

- Removing a concept the user has dropped (for example `perRelease`) means removing it everywhere in the chart repo: the template code, the `@schema` annotations, the regenerated `values.schema.json` (`mise run schema:helm`), the test case and its check lines, the README and the values.yaml comments. Then `grep -rni <term>` the working tree (the branch name and git history may keep the word), prove the other cases still render byte-identical with `cmp` against the base branch, and prove the removed key is refused with `additional properties '<key>' not allowed`. Do this as one extra commit on the MR branch, never by amend or force-push.

Single-consumer resources stay local. A resource that only one deployment repo needs (a PushSecret, an empty Secret that Helm keeps) is a template in that repo's own chart, not an addition to the shared chart it consumes. Put it in the shared chart only when the user asks for it; the user ruled this for the IAM Gate Init PushSecret and Secret on 2026-10-20 ("Ca ne doit pas être généralisé").

- Renaming a release, or changing a label that a Deployment selector uses, breaks the upgrade: `spec.selector` is immutable, so Helm fails with `cannot patch "<name>" with kind Deployment: ... spec.selector: ... field is immutable`. Keep the selector labels (`app.kubernetes.io/name`, `app.kubernetes.io/instance`) identical across a rename, or plan the Deployment deletion before the upgrade and name it in the MR. Three HelmReleases (feature-hub, flux-cd-prod, ui-authn-my-profile) failed this way when release names moved to constant names.

## Traefik static config (no phone-home)
- Turn off the version check and the anonymous usage report once, in the shared chart or template that defines the Traefik container, not per environment: static config `global: {checkNewVersion: false, sendAnonymousUsage: false}`, or the CLI flags `--global.checknewversion=false --global.sendanonymoususage=false`.
- Do not add an egress allow rule just to silence the log.
- Confirm the key is present on the rendered Deployment, and check the Traefik version it targets before relying on the key name. After rollout, confirm the pod logs no longer mention the update host.

## Acceptance tests
- Written by the `acceptance-writer` from spec criteria (catalogue: `~/.claude/agents/acceptance-writer.md`). Proven pattern (dry run 2026-10-28): helm-unittest over `templates/*.yaml` with `documentSelector` by kind + `matchMany`, JSONPath filter + `notExists` per container and initContainer, one test per values profile sharing assertions by YAML anchor. Relations between objects (Ingress → Service) need pytest over `helm template`: helm-unittest cannot compare two documents.
