description: Use when executing an implementation plan, after superpowers:writing-plans, in a GitHub or GitLab repo.

Wrapper over superpowers:subagent-driven-development (SDD, validated 6.4.2). Invoke SDD and follow it; the overrides below win. One plan task = one branch = one MR, stacked. Never merge on your own (see "Merging a stack"). The orchestrator writes no tests and no production code.

## Overrides to SDD
1. **Version.** `ls ~/.claude/plugins/cache/*/superpowers/`; not `6.4.2-*`: ledger `Warning: SDD <v> not validated`, re-read these overrides against its SKILL.md.
2. **Dispatch.** Order per task: acceptance-writer, red gate, implementer (green), mutant-writer, green gate with the sensitivity proof (step 4b). Sub-agents run no background process; an agent silent for more than ten minutes is stopped and relaunched (seen twice). The dispatch gives each agent the file where it writes its report. Every agent: `model: sonnet`, SDD's filled prompt plus slug, ID prefix, criterion IDs, spec path, mise task, worktree, branch. Before every dispatch `git status --short` is empty; else `git stash push -u -m "<slug> attempt <n>"` and ledger it. Task branch: `git switch -c feat/<slug> <branch N-1>` (task 1: `origin/<default>` or the branch the user names; the MR targets the same base).
3. **Red gate.** `subagent_type: acceptance-writer`; reply `ACCEPTANCE <sha>`: run `~/.local/bin/harness gate red --slug <slug> --test <sha> --task <task> --repo <worktree> --spec <spec> --ac <ID,...>`; quote exit code and last line. `--allow-compile-red` only after a ledgered `Ruling:`. FAIL: finding into fix rounds with the acceptance-writer. Gate output lines (`red` and `characterize`) include `CLAUSES <ID>: <n> in TESTS.md, <m> in spec`: the entry's "Alors" has a different clause count than the spec's, a transcription error; finding back to the acceptance-writer. PASS: dispatch `subagent_type: implementer` with the acceptance sha.
3b. **Commit order of a branch.** `docs(spec)` (spec committed: `SPEC NOT COMMITTED` otherwise) → `chore(tooling)` → `test(<slug>): acceptance` → `feat(<slug>)` → `refactor(<slug>)` / `fix(ci)`. The test task is wired (run by a commit hook or a CI job, directly or through `check`/`test`: else `NOT WIRED <task>`) before the first acceptance commit. When the base moves, redo the inventory of what the base already carries before dispatching.
4. **Green gate, in two steps.** (1) The implementer replies `DONE <feat sha>` or `DONE <feat sha> <refactor sha>` (an optional structural refactor, tests untouched), then its `UNTESTED <element> : <why>` lines for any behaviour no test asks for, without writing it. You rule on each: a real input or a spec line gives a criterion change and a test; otherwise ledger `Ruling: refused, hypothetical - <case>`. A test added afterwards and green at once is proved by removal: the implementer removes the targeted code, the test must turn red. (2) Mutant-writer (`subagent_type: mutant-writer`, `model: sonnet`) on the last commit of the task (the `refactor` commit when there is one): base = that sha, IDs, spec, worktree, out = `<sdd workspace>/proofs/<slug>/`; reply `MUTANTS <dir>`, `NO-MUTANT <ID> clause <n>: <reason>`, `NO-NEUTRAL <ID> : <reason>` or `BLOCKED`: rule it (`NO-NEUTRAL`: criterion removed, or rewritten, or "this detail is the contract" ledgered). Then run `~/.local/bin/harness gate green --slug <slug> --test <acceptance sha> --feat <sha> --task <task> --repo <worktree> (--proofs <dir> | --proof-exempt) [--ac-changed <ID,...>] [--replaces <slug,...>]`; quote exit code and last line. When the slug has several acceptance commits, `--test` is the LAST one. `green --proofs` refuses a modified tree (`TREE NOT CLEAN`, `FAIL`, nothing is applied): the implementer commits before the gate (PRV-012). `--feat` is the top of the branch being judged, checked out: `green` judges the working tree. `--proof-exempt` only for a task without behaviour change (`fix(ci)`, `docs`, `refactor` under existing tests), only after a ledgered `Ruling:`. Lines: `MUTANT MISSING <ID> clause <n>` (patch absent: resume the mutant-writer), `SURVIVED <ID> clause <n>` (no test dies: test too weak, or equivalent mutant), `BRITTLE <ID>` (a neutral change fails a test: the test pins a detail), `REDUNDANT <ID>: covered by <ID>`, `KEPT TEST MODIFIED <file> <ID>` (a kept test changed: only `--ac-changed`/`--replaces` allow it), `INCOMPLETE <ID>` (entry without Étant donné/Quand/Alors), `NOT WIRED <task>`, `PROOF MISSING` (neither `--proofs` nor `--proof-exempt`), `REPORT missing: <task> n'a pas écrit <path>`. FAIL: finding into SDD fix rounds with the implementer. Only then SDD's task review; its dispatch carries `git show --stat --format="%h %s" <acceptance sha> <sha>` and the rubric: is each criterion observable at the boundary? does each acceptance test check the "Alors", and only it? which behaviour-neutral change would break it (any answer is a finding)? did the acceptance-writer depend on implementation details? Hypothetical edge cases are out of scope (template rule "Pas de cas aux limites hypothétiques"): the reviewer reports an edge case only with the real input or spec line that produces it, and flags as a finding any test or code that handles a case with neither.
4b. **Per task, the sensitivity proof only (default).** The neutral change does not run on each task: the mutant-writer dispatch says `no neutral change` and `green` gets `--no-neutral` (output line `NEUTRAL SKIPPED`); one mutant per clause, `SURVIVED` and `REDUNDANT` are judged as in step 4. `green` and `characterize` take `--jobs <n>`: the proofs are judged n at a time, each on a throwaway worktree of `HEAD`, the working tree untouched. Use it when the test task runs from a fresh checkout (nothing it needs is untracked: installed dependencies, downloaded charts, provider cache) and binds no fixed port nor shared path; `MUTANT INVALID <ID> clause <n>: no result` on every mutant says it does not: drop `--jobs`. The neutral change runs in `characterize` and in rewrite mode, which keep it mandatory, and on a task only when the user asks for full proofs ("preuves complètes"): then `green` runs without `--no-neutral`.
5. **Contested criterion.** `CRITERION-ISSUE <ID>: <reason>`, `TESTS-CHANGE <ID>: <reason>` or a reviewer finding: rule it (a finding about a case with no real input and no spec line is refused, never turned into a criterion, test or code: ledger `Ruling: refused, hypothetical - <case>`), ledger `Ruling: <what> - <why> - <cost if wrong>`. Boundary does not exist yet: ruling (a) resume the acceptance-writer with `compile-red permitted`, red with `--allow-compile-red`; or (b) insert a skeleton task before this one. Transcription error: resume the acceptance-writer with the ruling and the old acceptance sha; it rebuilds `test(<slug>): acceptance` from its parent (any `feat` commit is dropped), red again (step 3), then re-dispatch the implementer with the new sha. Criterion change: also ledger `Criterion change: <ID> <old> → <new> — <why>`, the orchestrator edits the spec and commits it `docs(spec)` (the only spec edit it makes). Once code exists, never amend: the acceptance-writer adds a NEW acceptance commit; `green` then takes the LAST acceptance commit in `--test` and `--ac-changed <ID>`. Before any code exists, the acceptance-writer rebuilds as above and red runs again. Refused: resume the sender with the ruling.
5b. **Replies.** A reply without a usable sha: take `git rev-parse HEAD` in the worktree, check `git log -1` matches the expected commit type, ledger it. `green` always uses the top slug of the branch (it checks every `TESTS.md` ID); "no behaviour change" tasks pass the top slug's acceptance sha.
5c. **Characterize.** Plan task field `Mode: characterize` (default `atdd`): already-green behaviour, no implementer. Flow: acceptance-writer (dispatch adds "characterization: tests expected green; replaces <slugs>"; reply `ACCEPTANCE <sha>`), then `subagent_type: mutant-writer` (`model: sonnet`; base = acceptance sha, IDs, spec, worktree, out = `<sdd workspace>/proofs/<slug>/`; reply `MUTANTS <dir>`, `NO-MUTANT <ID> clause <n>: <reason>`, `NO-NEUTRAL <ID> : <reason>` or `BLOCKED <reason>`: rule it), then `~/.local/bin/harness gate characterize --slug <slug> --test <sha> --task <task> --repo <worktree> --spec <spec> --ac <ID,...> --proofs <dir> [--replaces <slug,...>] [--ac-changed <ID,...>]` with `HEAD` = the acceptance commit (the gate refuses otherwise: `HEAD IS NOT --test`); quote exit code and last line. Lines `KILLED`, `SURVIVED`, `MUTANT MISSING`, `MUTANT INVALID`, `BRITTLE`, `REDUNDANT`, `BASELINE NOT GREEN`, `REPLACED <slug>: <file or ID>`. `SURVIVED <ID>`: ruling, test too weak (resume the acceptance-writer) vs equivalent mutant (resume the mutant-writer); ledger it, re-run. `MUTANT INVALID`: resume the mutant-writer. `BASELINE NOT GREEN` on a new ID = real bug: ruling, that ID switches to ATDD (red gate, implementer, green). `green` takes `--replaces` too. MR body: block "Tests remplacés" from the `REPLACED` lines. Review: transcript check, the mutant-writer read no test path (`TESTS.md` included; it may read `mise.toml` when the code under test lives in it).
6. **Models.** Acceptance-writer, implementer, task reviewer, scoped re-reviews: `sonnet` (or `haiku`). Fix rounds 4-5: fresh Sonnet implementer, never a more capable model. Only step 8 may exceed Sonnet.
7. **Per task, after green and review approved.** Push; open the MR with the forge skill (base = branch N-1; body: criterion IDs with titles, link to the `TESTS.md` section as `<project web_url>/-/blob/<branch>/TESTS.md`, GitHub `/blob/<branch>/TESTS.md`, plus the heading as text; a "Critères modifiés" block on top when any). Start the next task without waiting for CI. Never edit `TESTS.md` yourself.
8. **End.** The final review: SDD's final whole-branch review, dispatch description `final review <stack>`, `model: opus`, read-only. When the repo has a stack skill, the brief names the hexagonal skill of its language (`hexagonal-go`, `hexagonal-py`): a SOLID or layering remark cites the code it targets and goes through "Work without a test" (commit `refactor`, `green` replayed with the proofs). Retain only remarks on real cases (real input or spec line cited); each goes through "Work without a test". Hypothetical edge cases are refused and ledgered as in step 5. Before that review, when a task of the stack used `--replaces` or `--ac-changed`: the mutant-writer in replay mode writes mutants on the stack's base (production code alone), then run `~/.local/bin/harness gate replay --repo <worktree> --base <base sha> --head <head sha> --proofs <dir> --task <task>` (one task, repeat the call per task); the task first runs without any mutant on the base and on the head: `BASELINE NOT GREEN base|head` and `FAIL` when it fails, then repair the task or the environment before replaying (RPL-003); lines `KEPT <name>`, `NEVER <name>`, `GAINED <name>`, `LOST <name>`. `LOST`: the stack lost a protection, a failure unless `--accept-lost <name>` (repeated once per accepted loss) after a ledgered `Ruling:`. Then watch CI of all MRs with Monitor (forge skill). Red: superpowers:systematic-debugging phases 1-3, reproduction = criterion of a fix task, then "Rebase and conflicts".
9. **Finish.** Do not invoke finishing-a-development-branch. Write the status report listing every `Criterion change:` first, then every `Ruling:` from the ledger, then stop with the MR links. Never merge on your own, never propose lifting a hook.
10. **Blockers.** `BLOCKED <reason>` and missing tool: rule it (propose adding the tool to `mise.toml`; install nothing outside the repo). Stop for the user only on merge, security-sensitive or irreversible action, plan broken beyond a guess; artifact with numbered options and a recommendation, chat gets link and choice.

## Setup
1. Worktree for the whole stack: superpowers:using-git-worktrees. Enter it (EnterWorktree, or start the session there) before dispatching any agent; agents `cd <worktree>` at the start of every Bash call (the worktree hook judges commits by the call's cwd).
2. Forge, run in the repo (`gh` for GitHub, `glab` otherwise; then follow `forge-gh` / `forge-glab` for MRs, CI, status):
```bash
forge=$(~/.local/bin/harness local forge --repo .) || exit 1
```
Internal hosts are declared in `~/.claude/local/forges` (`<host> <tool>` per line), a directory that is never versioned.
Unknown host (or a local-path origin): stop and say so to the user.
3. Repo not conforming to `repo-tooling` (no `mise.toml` with `setup`/`test`/`check`, no prek config): feature 1 is `chore(tooling)` (see "Work without a test").
3b. Stack: invoke `repo-stack` at the repo root and follow the stack skill it names. A repo that has a stack and not its baseline (no `ARC-…` entry in `TESTS.md`; no `FAC-…` entry while it has a `Dockerfile`) starts its stack with the baseline tasks, after `chore(tooling)`: `Mode: characterize` when the code already complies, `atdd` otherwise (the architecture test is red, the implementer moves the code). Before installing it, check that no `TESTS.md` entry already uses an `ARC-…` or `FAC-…` ID for something else; if one does, stop and tell the user. Once installed, the baseline is held by the gate like any criterion (`green` checks every `TESTS.md` ID, `replay` replays its mutants).
4. No CI pipeline: stop and tell the user. Check GitLab: `glab api projects/:id | jq -r .ci_config_path` and `git ls-files .gitlab-ci.yml`; GitHub: `ls .github/workflows`. An include-only CI counts.
5. Each plan task = one feature = one slug, one ID prefix, one mise task, one branch.

## Work without a test
Who does what (the orchestrator still writes nothing):
- Behaviour change (CI red on a test, behavioural review remark on a real case; a hypothetical edge case gets no fix, see step 5): if the cause is unknown, first superpowers:systematic-debugging phases 1-3 (no red/green, throwaway code); once the root cause is proven, you write the fix criterion (ID + Étant donné/Quand/Alors from the root cause) at the end of the plan's fix task under `## Critères d'acceptation`, and the acceptance-writer transcribes it (steps 3-4 on the faulty branch, `--spec` = the plan file). A wrong test follows step 5, never an in-place edit.
- Non-behavioural fix (lint, formatting, docs, rename, CI config): the `implementer` alone, brief says "no behaviour change" and the commit type (`fix(ci)`, `refactor`, `docs`); then green mode with the branch's acceptance sha and the new sha. A commit that touches no production or test file (docs, CI config): green with `--proof-exempt`; the proofs were judged on the `feat`/`refactor` commit. A commit that touches code (refactor, rename, lint, formatting): green with `--proofs <dir>` (the proofs are replayed).
- Direct fix (only when the user says `fix direct` or `sans TDD`; never your own choice): no SDD, no acceptance-writer, no mutant-writer, no `harness gate`, no ledger. In the worktree, `git switch -c fix/<slug> origin/<default>`; you write the fix yourself and commit it `fix(<scope>): <summary>`. Existing tests still guard: the diff touches no test file and not `TESTS.md` (`git diff --name-only origin/<default>..HEAD`, quote it), and `mise run check` is green (quote its last line); a kept test that has to change ends the direct fix: stop and say so. Push, open the MR with the forge skill, body starting with "Fix direct, sans test d'acceptation" and what was run; watch CI until green, then stop with the MR link.
- `chore(tooling)`: the `implementer` applies `repo-tooling`, no `TESTS.md` section. Gate: you re-run `mise run check` and `prek run --all-files` (they are read-only) and quote them.

## Mode: rewrite
For a repo whose `TESTS.md` has sections in the old format: a stack where each task takes one test file in `characterize --replaces <old slugs>`. Entries are rewritten in the new format (criterion in full: Étant donné / Quand / Alors); each test passes the three proofs (sensitive, neutral-stable, non-redundant); a test that fails one is removed or rewritten (`Criterion change:`, rewritten tests go through `--ac-changed`); the stack ends with `replay` base against head. The mutants for `replay` are written on the base. Applying it repo by repo is planned elsewhere.

## Rules worth the repetition
- A sub-agent's report is a claim: re-run the decisive check yourself and quote command and output; a number enters the ledger only after you read the output.
- An acceptance file starts the product only through the common helpers of the test repository, so a proof made mandatory later turns no earlier file red.
- A test task that manipulates repositories and is launched from a git hook begins with `unset $(git rev-parse --local-env-vars)`.

## Merging a stack
Only when the user asks for it, in that message, for the stack or the merge request they name. An earlier go does not carry over.
1. Stack behind the default branch: rebase it first ("Rebase and conflicts"), wait for green pipelines, and say what the default branch brought in.
2. `harness merge-stack --dry-run <top MR>`: every obstacle is named (`OUTDATED`, `NOT STACKED`, `DRAFT`, `CHECKS FAIL`). Fix what is yours to fix, report the rest.
3. `harness merge-stack <top MR>` (add `--validate '<repo check command>'` when the repo has no pipeline). The hook asks the user; their go covers this stack only. Never call `gh pr merge` or `glab mr merge`.
4. Last line `PASS`: report the merged MRs and quote `TREE IDENTICAL` and the check line. Last line `FAIL`: stop and report the output as is (`STOPPED`, `MERGED:`, `REMAINING:`, `TREE DIFFERS`, `CHECKS FAIL`). Repair nothing, revert nothing, do not run it again without a new go.

## Rebase and conflicts
- Base moves during the stack (review on MR N-1): `git rebase --update-refs` from the top, `git push --force-with-lease` each moved branch. Afterwards every test and feat sha above has changed: re-run `harness gate green` on each moved branch with its new shas (`git log --format='%h %s' <base>..<branch>`) before pushing.
- `TESTS.md` carries `merge=union` (`.gitattributes`). If a conflict still occurs, you may keep both sections verbatim (the only allowed `TESTS.md` edit), then re-run green on each moved branch.

## Status report
On request ("status report", "où en est-on", "topo") and at the end of a stack: one Docs artifact per workstream, updated at the same link. Sections: where we are (MR table read via `gh`/`glab` just before writing), what remains, what awaits a decision, evidence. Chat: short result and link.

Templates: `templates/acceptance-criteria.md` (spec criteria), `templates/TESTS.md`.
