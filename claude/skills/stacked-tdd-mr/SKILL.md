Wrapper over superpowers:subagent-driven-development (SDD, validated 6.4.2). Invoke SDD and follow it; the overrides below win. One plan task = one branch = one MR, stacked. Never merge on your own (see "Merging a stack"). The orchestrator writes no tests and no production code.

## Overrides to SDD
1. **Version.** `ls ~/.claude/plugins/cache/*/superpowers/`; not `6.4.2-*`: ledger `Warning: SDD <v> not validated`, re-read these overrides against its SKILL.md.
2. **Dispatch.** Order per task: acceptance-writer, implementer (code and its unit tests), then `MUTATION_BASE=<branch N-1> mise run check` (it runs `mutation`), then coverage (step 4c) when the repo has a stack skill. Sub-agents run no background process; an agent silent for more than ten minutes is stopped and relaunched (seen twice). The dispatch gives each agent the file where it writes its report. Every agent: `model: sonnet`, SDD's filled prompt plus slug, ID prefix, criterion IDs, spec path, mise task, worktree, branch. Before every dispatch `git status --short` is empty; else `git stash push -u -m "<slug> attempt <n>"` and ledger it. Task branch: `git switch -c feat/<slug> <branch N-1>` (task 1: `origin/<default>` or the branch the user names; the MR targets the same base).
3. **Acceptance.** `subagent_type: acceptance-writer`; reply `ACCEPTANCE <sha>` (commit `test(<slug>): acceptance`). Then dispatch `subagent_type: implementer` with the acceptance sha.
3b. **Commit order of a branch.** `docs(spec)` (spec committed) → `chore(tooling)` → `test(<slug>): acceptance` → `feat(<slug>)` → `refactor(<slug>)` / `fix(ci)`. Nothing checks this order any more. When the base moves, redo the inventory of what the base already carries before dispatching.
4. **Mutation.** (1) The implementer replies `DONE <feat sha>` or `DONE <feat sha> <refactor sha>` (an optional structural refactor, tests untouched), then its `UNTESTED <element> : <why>` lines for any behaviour no test asks for, without writing it. You rule on each: a real input or a spec line gives a criterion change and a test; otherwise ledger `Ruling: refused, hypothetical - <case>`. (2) You run `git fetch origin && MUTATION_BASE=<branch N-1> mise run check` in the worktree (CI runs `mise run mutation` with the MR's target branch as `MUTATION_BASE`) and quote the exit code and last line. The fragments are in `repo-tooling` ("Mutation"). A surviving or uncovered mutant is a finding for the implementer: it adds the unit test that kills it, or removes the code nothing asks for (`UNTESTED`). An equivalent mutant is excluded in the tool's configuration (pytest-gremlins pardon capped by `max_pardons`, `--exclude-mutators` / `--exclude` for helm-mutation-test, `-E` for gremlins) and ledgered as `Ruling:`. Only then SDD's task review; its dispatch carries `git show --stat --format="%h %s" <acceptance sha> <sha>` and the rubric: is each criterion observable at the boundary? does each acceptance test check the "Alors", and only it? did the acceptance-writer depend on implementation details? Hypothetical edge cases are out of scope (template rule "Pas de cas aux limites hypothétiques"): the reviewer reports an edge case only with the real input or spec line that produces it, and flags as a finding any test or code that handles a case with neither.
4c. **Coverage.** After `mise run check` of each task, only when `repo-stack` names a stack skill (a repo without one skips the step). It proves that every block of production code is run by the boundary tests; it reads no slug. Detail: `claude/docs/specs/2026-11-16-couverture-de-frontiere-design.md` in the `Wihrt/mise` repo.
   - Command: `~/.local/bin/harness gate coverage --task test --repo <worktree> --coverage .tdd/cover/go.txt` and/or `--coverage .tdd/cover/py.lcov` (repeatable, one per report the repo's test task writes). Quote exit code and last line.
   - Exit: last line `PASS` (exit 0) or `FAIL` (exit 1). `ERROR: <msg>` then `FAIL`, exit 2, is a usage or environment error (not a git repository, unreadable report, unknown report format, malformed `COVERAGE.md`), not a finding: repair the call or the repo, do not send it to the implementer.
   - `TASK FAILED <task>`: the test task failed, repair it first. `COVERAGE missing: <task> n'a pas écrit <path>`: report absent, fix the test task. `COVERAGE <path>: <n> files`, `ACCEPTED <file>[:<start>-<end>]: <reason>` (covered by an entry of `COVERAGE.md`), `ERROR RETURNS IGNORED <n>` (a Go block is set aside and counted when one of the results of its `return` names the tested error, `return "", err` or `return fmt.Errorf("…: %w", err)`; a `return` that does not name it is judged), `NOT JUDGED <n> files: neither Go nor Python`: information.
   - `UNCOVERED <file>:<start>-<end>` (a block no test runs), `UNCOVERED BRANCH <file>:<line>` (a Python branch never taken), `NOT MEASURED <file>` (a tracked file absent from the reports): finding for the implementer, who removes the code or answers `UNTESTED`. You rule as for `UNTESTED`: one more criterion, or an entry in `COVERAGE.md` after a ledgered `Ruling:`; when you refuse it (hypothetical), the implementer removes the code and the step runs again.
   - `PRAGMA <file>:<line>` (a `no cover` or `no branch` pragma comment, in any spelling coverage.py honours; also a line-exclusion key `exclude_lines`, `exclude_also`, `partial_branches`, `partial_branches_always` or `partial_also` in the report section coverage.py reads in `.coveragerc`, `setup.cfg`, `tox.ini` or `pyproject.toml`): the implementer removes it; no entry ever accepts it. `STALE EXCEPTION <file>: <text>` (an entry that excuses nothing any more): you remove it.
   - `COVERAGE.md`: only the orchestrator writes it, and only after a ledgered `Ruling:`. Under a `## <file>` section, an entry is one line, ``- `<text>` : <reason>`` or `- fichier entier : <reason>`; the reason is mandatory. `<text>` is the first line of the block as `UNCOVERED` locates it (its start line), trimmed; it accepts every finding of that file with that first line. It is a Markdown code span: delimited by as many backticks as needed to exceed the longest run of backticks it contains, with one space on each side when it starts or ends with a backtick. Only `fichier entier` accepts `NOT MEASURED`. A Go block that only returns an error is already set aside: an entry written for it accepts nothing and is `STALE EXCEPTION`.
   - `--baseline`: once, when an existing repo adopts the gate, after a `Ruling:`. It adds the findings not accepted yet as entries with reason `dette initiale`, and those findings stop failing. `PRAGMA`, `STALE EXCEPTION`, `COVERAGE missing` and `TASK FAILED` still end in `FAIL`; in the last two nothing is written.
5. **Contested criterion.** `CRITERION-ISSUE <ID>: <reason>` or a reviewer finding: rule it (a finding about a case with no real input and no spec line is refused, never turned into a criterion, test or code: ledger `Ruling: refused, hypothetical - <case>`), ledger `Ruling: <what> - <why> - <cost if wrong>`. Boundary does not exist yet: ruling (a) resume the acceptance-writer with `compile-red permitted`, or (b) insert a skeleton task before this one. Criterion change: also ledger `Criterion change: <ID> <old> → <new> — <why>`, the orchestrator edits the spec and commits it `docs(spec)` (the only spec edit it makes), and the acceptance-writer adds a NEW acceptance commit (once code exists, never amend). Refused: resume the sender with the ruling.
5b. **Replies.** A reply without a usable sha: take `git rev-parse HEAD` in the worktree, check `git log -1` matches the expected commit type, ledger it.
6. **Models.** Acceptance-writer, implementer, task reviewer, scoped re-reviews: `sonnet` (or `haiku`). Fix rounds 4-5: fresh Sonnet implementer, never a more capable model. Only step 8 may exceed Sonnet.
7. **Per task, after mutation and review approved.** Push; open the MR with the forge skill (base = branch N-1; body: criterion IDs with titles, link to the spec section; a "Critères modifiés" block on top when any). Start the next task without waiting for CI.
8. **End.** The final review: SDD's final whole-branch review, dispatch description `final review <stack>`, `model: opus`, read-only. When the repo has a stack skill, the brief names the hexagonal skill of its language (`hexagonal-go`, `hexagonal-py`): a SOLID or layering remark cites the code it targets and goes through "Work without a test" (commit `refactor`, `mise run check` green). Retain only remarks on real cases (real input or spec line cited); each goes through "Work without a test". Hypothetical edge cases are refused and ledgered as in step 5. Before that review: the coverage step (4c) on the top of the stack, checked out. Then watch CI of all MRs with Monitor (forge skill). Red: superpowers:systematic-debugging phases 1-3, reproduction = criterion of a fix task, then "Rebase and conflicts".
9. **Finish.** Do not invoke finishing-a-development-branch. Write the status report listing every `Criterion change:` first, then every `Ruling:` from the ledger, then stop with the MR links. Never merge on your own, never propose lifting a hook.
10. **Blockers.** `BLOCKED <reason>` and missing tool: rule it (propose adding the tool to `mise.toml`; install nothing outside the repo). Stop for the user only on merge, security-sensitive or irreversible action, plan broken beyond a guess; artifact with numbered options and a recommendation, chat gets link and choice.

## Setup
1. Worktree for the whole stack: superpowers:using-git-worktrees. Enter it (EnterWorktree, or start the session there) before dispatching any agent; agents `cd <worktree>` at the start of every Bash call (the worktree hook judges commits by the call's cwd).
2. Forge, run in the repo (`gh` for GitHub, `glab` otherwise; then follow `forge-gh` / `forge-glab` for MRs, CI, status):
```bash
forge=$(~/.local/bin/harness local forge --repo .) || exit 1
```
Internal hosts are declared in `~/.claude/local/forges` (`<host> <tool>` per line), a directory that is never versioned.
Unknown host (or a local-path origin): stop and say so to the user.
3. Repo not conforming to `repo-tooling` (no `mise.toml` with `setup`/`test`/`check`, no prek config): feature 1 is `chore(tooling)` (see "Work without a test").
3b. Stack: invoke `repo-stack` at the repo root and follow the stack skill it names. A repo that has a stack starts its stack with the baseline tasks (architecture test, and a container test while it has a `Dockerfile`), after `chore(tooling)`. A test task that writes its report elsewhere than `.tdd/junit.xml` (`test:api`, `test:ui`, `test:container`) gets `--report <path>` on the coverage command of its tasks.
4. No CI pipeline: stop and tell the user. Check GitLab: `glab api projects/:id | jq -r .ci_config_path` and `git ls-files .gitlab-ci.yml`; GitHub: `ls .github/workflows`. An include-only CI counts.
5. Each plan task = one feature = one slug, one ID prefix, one mise task, one branch.

## Work without a test
Who does what (the orchestrator still writes nothing):
- Behaviour change (CI red on a test, behavioural review remark on a real case; a hypothetical edge case gets no fix, see step 5): if the cause is unknown, first superpowers:systematic-debugging phases 1-3 (no red/green, throwaway code); once the root cause is proven, you write the fix criterion (ID + Étant donné/Quand/Alors from the root cause) at the end of the plan's fix task under `## Critères d'acceptation`, and the acceptance-writer transcribes it (steps 3-4 on the faulty branch, spec = the plan file).
- Non-behavioural fix (lint, formatting, docs, rename, CI config): the `implementer` alone, brief says "no behaviour change" and the commit type (`fix(ci)`, `refactor`, `docs`); then `mise run check` green.
- Direct fix (only when the user says `fix direct` or `sans TDD`; never your own choice): no SDD, no acceptance-writer, no ledger. In the worktree, `git switch -c fix/<slug> origin/<default>`; you write the fix yourself and commit it `fix(<scope>): <summary>`. Existing tests still guard: the diff touches no test file (`git diff --name-only origin/<default>..HEAD`, quote it), and `mise run check` is green (quote its last line); a kept test that has to change ends the direct fix: stop and say so. Push, open the MR with the forge skill, body starting with "Fix direct, sans test d'acceptation" and what was run; watch CI until green, then stop with the MR link.
- `chore(tooling)`: the `implementer` applies `repo-tooling`. Gate: you re-run `mise run check` and `prek run --all-files` (they are read-only) and quote them.

## Rules worth the repetition
- A sub-agent's report is a claim: re-run the decisive check yourself and quote command and output; a number enters the ledger only after you read the output.
- An acceptance file starts the product only through the common helpers of the test repository, so a proof made mandatory later turns no earlier file red.
- A test task that manipulates repositories and is launched from a git hook begins with `unset $(git rev-parse --local-env-vars)`.

## Merging a stack
Only when the user asks for it, in that message, for the stack or the merge request they name. An earlier go does not carry over.
1. Stack behind the default branch: rebase it first ("Rebase and conflicts"), wait for green pipelines, and say what the default branch brought in.
2. `harness merge-stack --dry-run <top MR>`: every obstacle is named (`OUTDATED`, `NOT STACKED`, `DRAFT`, `CHECKS FAIL`). Fix what is yours to fix, report the rest.
3. `harness merge-stack <top MR>` (add `--validate '<repo check command>'` when the repo has no pipeline). The hook asks the user; their go covers this stack only. Never call `gh pr merge` or `glab mr merge`.
4. Last line `PASS`: report the merged MRs and quote `TREE IDENTICAL` and the check line. Last line `FAIL`: stop and report the output as is (`STOPPED`, `MERGED:`, `REMAINING:`, `TREE DIFFERS`, `CHECKS FAIL`). Repair nothing, revert nothing, do not run it again without a new go.

## Rebase and conflicts
- Base moves during the stack (review on MR N-1): `git rebase --update-refs` from the top, `git push --force-with-lease` each moved branch, then `git fetch origin && MUTATION_BASE=<branch N-1> mise run check` on each moved branch before pushing.

## Status report
On request ("status report", "où en est-on", "topo") and at the end of a stack: one Docs artifact per workstream, updated at the same link. Sections: where we are (MR table read via `gh`/`glab` just before writing), what remains, what awaits a decision, evidence. Chat: short result and link.

Templates: `templates/acceptance-criteria.md` (spec criteria).
