---
name: parallel-repo-plan-dispatch
description: Use when running a multi-repo plan, or sweeping or auditing many repo clones, with parallel subagents.
category: subagent-workflow
---

Dispatch implementers in parallel only over disjoint repositories, and give each one a brief file in the workspace instead of inline prose.

- Before a fan-out pushes to existing MR branches (`--force-with-lease`, rebase, rewrite), the lead states in one short paragraph the change each lot will make, and waits for the user's explicit yes. When the lead has to infer what "la modification attendue" means, that inference is not a go: ask first, then dispatch. The same holds for a premise about the base branch (for example "the base branch is migrated to the shared chart"): before dispatch, run `git -C REPO ls-tree -r --name-only origin/BASE` on every repo of the lot. One repo whose MR shows the migration does not establish it for the others; one day three repos still carried their own chart templates on the base branch, and the lots had been briefed on the wrong premise.

- Read-only sweeps over many clones (an audit, an inventory, a liveness check) follow the same dispatch: one Sonnet agent per lot of about four clones, each returning a table file and a status line. The lead merges the tables. Do not run one long loop over 10 or more repositories in the lead session. For the audit itself, use `gitlab-project-liveness-audit`.

- Write the shared instructions once, in a file outside any repository tree (for example under `.superpowers/sdd/PLAN/`). Each agent prompt says "read this file first" and names the plan sections to read. Starting point: `templates/task-brief.md`.
- Pilot a cross-repo change on one repository first. Read its diff, its checks and its MR state yourself, then put the validated text in the shared brief as the model every lot copies.
- A pilot that stops BLOCKED on its own pre-push gate is a ruling for the lead, not a go for the fan-out. Hold every lot, settle the option with the user, add the gate to the shared brief as a numbered complement, and only then dispatch the lots.
- When one file (a script, its tests, its lock file) must be copied verbatim into repos with different layouts, pilot on one repository per layout (for example a chart in a subfolder and a chart at the root). The brief keeps the file byte-identical and passes every difference through variables in the task file. Record the sha1 of each copied file in progress.md, and recheck it at each hand-back.
- When the user changes the design after MRs are already open, run the same order again: write a round-2 brief file, pilot one repository on the existing branch and MR (new commit, no second MR), check its render against the previous head yourself, append a "Validated model" section with the exact template, values style, description wording and commands, then resume the finished agents via SendMessage and point them at that section.
- When the base branch gained a job or file that open MRs lack (for example a helm-diff job added to `bleu` after the MRs were opened), the brief brings each feature branch up to the base with `git merge origin/<base>` under the commit identity flags, then a simple push. No rebase, no force-push: the MR keeps its history and its notes, and its pipeline re-runs on the new head. A conflict is resolved by keeping both sides' intent (the new job and the migrated chart); an agent that cannot keep both stops BLOCKED with the conflicting paths.
- Fan-out agents reproduce the brief's commands and text verbatim. When an agent substitutes its own variant (for example an upstream install line in place of the brief's), it must report that as a finding; the lead decides whether to accept it.
- Before partitioning, grep every target repo on its base ref for each name the platform will own (pull secret, registry, namespace, Vault role) and for each old name it replaces (`git -C <repo> grep -n '<old>' origin/<base>`). Freeze the agreed value in the shared brief as a numbered complement before any lot starts. A value decided after the branches were converted costs a fix round per repo: in the 2NA run the pull secret moved from `artifactory-docker-2na` to `artifactory-docker` after the converted branches already used the old name, and tasks reached `fix round 2/5` and `fix round 3/5`.
- Before partitioning a CI change, read each repository's CI template and its recent pipeline sources (`source` field of `glab api projects/<id>/pipelines`). A repository whose workflow never admits `merge_request_event` cannot run MR-gated jobs: put it in its own lot, and get the user's decision on the workflow change before anyone pushes. Use `gitlab-ci-mr-pipeline-source`.
- Enumerate branches, not only the feature branch. For each target repo run `git ls-remote --heads origin '<feat>*'` and list the open MRs per branch (`glab api "projects/:id/merge_requests?source_branch=<feat>-<env>&state=all"`). When the user asks for "all repos/branches", every per-environment branch with an open MR is a target with its own base. Before partitioning, get the user's ruling for any branch whose base lacks the platform resource the new design relies on.
- Re-derive the plan's inventory right before partitioning. A task that lists "repos without X" goes stale once an MR merges. For every listed repo run `git -C <repo> ls-tree -r --name-only origin/<base> <path>` and `glab mr list --source-branch <feat> -A`, drop what already landed, and record the drop as a ruling in progress.md. Evidence: the 14/10 inventory listed repos that by 15/10 already had their helm-diff files on `bleu` and whose feature MRs were merged; every repo on the list was stale. Judge activity by human commits, not by `last_activity_at`: a scheduled pipeline bumps that field. Read the author set of `main` (`glab api "projects/<id>/repository/commits?ref_name=main"`) and the pipeline schedules; a repo whose commits all come from one person on a nightly job is a personal tool, and the user rules whether it stays in scope. Before asking the user to rule on such a repo, give each in-scope repo a one-line purpose from its README (what it does, who runs it); the user otherwise has to ask what it is after its MR is already in the pilot.
- When the user orders groups of repos ("1XM d'abord, puis les repos 2NA"), that order is a gate, not a suggestion: pilot and lots of the first group run, the user reviews the first group's pilot, and no lot of the next group starts until every first-group lot has handed back. Write the order as its own section in the plan and in progress.md before the first dispatch.
- When the twin MR's diff does not apply to a repo on another base (the 1XM patch failed on 2NA `bleu`), the lot redoes the same additions with an edit script that asserts one match per anchor and reports zero removed lines. It does not force the patch in with `--3way` or by hand.
- A snippet copied from a reference repo into a lot's brief or fix round is located by an anchor (`grep -n` on the job's name line, then `sed -n` between two anchors), never by line numbers read from a view of another file. A copy taken one line off (the `mise install` line plus its comment, instead of the comment plus the login line) put a 403 back into three repos and cost each one two throwaway commits. Diff the copied block against the reference before the first push, and expect exactly one commit per fix.

- Give every lot's scratch files a repo-specific name (`avant-<slug>.txt`), never a shared name in the scratchpad. Every brief forbids `rm`, `rm -rf` and any other deletion, inside scratch directories and repositories alike: a reviewer that tries to clear a path it wrote earlier must use a fresh name instead. The user stopped a review agent for exactly this ("Drop the rm; use fresh names"), and it left no report file behind. Two pilots wrote the same reference file, and one lot's `.git` before/after check then compared against the wrong baseline. Helper files count too: a `common.sh` sourced by several lots was overwritten by another lot in the shared scratchpad, so each lot keeps its helpers in its own directory and the brief names that directory.
- Never test a clean base with `git stash` inside a worktree: the stash lives in the `.git` shared with the main clone. For that comparison, create a detached worktree on `origin/<base>`.
- Re-derive the linter, runtime and language versions from the repo (`package.json` scripts, the CI image in `.gitlab-ci.yml`, `.nvmrc`, `engines`, the Dockerfile), not from the inventory. An inventory line naming eslint/prettier sat beside a repo that runs Biome, and a version cell reading `-` had no source. Each lot names the file it took the value from.
- Partition the repositories so that no two agents touch the same one. Group small repositories into lots of about four per agent to bound the agent count. Two agents working in worktrees of the same clone share its `.git`: serialize them, or give one read-only work. Each brief forbids `mise install` in a worktree (its postinstall rewrites the shared git hooks) and carries the `GIT_*` unset loop for any script a hook launches.
- Every prompt states: model `sonnet`; commits with `git -c user.name=... -c user.email=...` on every commit-creating command, including `git merge`, `git commit --amend` and `git rebase` (a merge run without the flags took the machine's default identity); no AI attribution in commits or merge requests; never merge unless the current user request names the MRs to merge; in that case the brief lists only those MRs with their expected head sha, and the agent merges nothing else; watch the pipeline with a bounded wait; stop and report rather than guess; no cluster or secret-store writes unless the plan asks for them; run `mise trust` in each new worktree before any task that runs Python.
- Each brief says the agent ends with no background process of its own: no `until`/`sleep` monitor left running after its verdict. A finished agent still waiting on one reports as running. When a hand-back arrives with such a wait still open, the lead checks the verdict through the API, then stops the agent with `TaskStop`. A `TaskStop` on an already-completed task only returns an error.
- Each brief tells its lot to check the MR pipeline's `merge_request_event` jobs before any push, as `gitlab-ci-lint-simulation` requires. A job that writes outside the repo (Jira sync with `DRY_RUN` off, a deploy, a notification, a load test) stops that repo as `bloqué-effets-CI`, unpushed, until the lead decides.
- A repo whose `sonar` job is red on its MR while green on its target: the lot stops with status `bloqué-sonar` and reads no Sonar data itself. The lead gives the user the MR and the `sonar-quality-gate-diagnosis` route; the diagnostic step waits for the user's yes.
- Shared branches (`-dev`, `-main`, `-azure`, or any branch other teams read) can be refused by the permission classifier ("Modify Shared Resources") on the first `git merge` or push, even when the user asked for the work. Before dispatch, list the write targets per branch and get the user's explicit authorization for the shared ones, or a permission rule. A refused agent stops and reports; the lead escalates to the user and never routes around the refusal. Lots that only wrote to the owned feature branch completed while the shared-branch lots stopped on their first merge. A general go-ahead such as "all repos and branches" did not clear the classifier for these writes, and neither did a "Go" typed by the user and relayed by the lead into each agent's brief: every relaunch of the same operations was refused again. After one refusal of a shared-branch write, do not relaunch lots on it. Stop the fan-out, try the first blocked write once in the lead's own session (which carries the user's message), and report the refusal to the user with the unblock options: a Bash permission rule, or running the writes in the main session. Ask once, before the first lot starts, with the operations listed per branch class: merge of the base, commit, push, worktree creation, and `glab mr update` of the title and description of existing MRs. Shared-branch briefs tell the agent to commit locally and stop before any push, so a refusal leaves one batch of local commits awaiting a single decision; the lead records each refused operation in progress.md. A scope widened mid-run (a new branch class) goes by SendMessage addendum to every agent that stopped on the narrower brief, and finished lots are not re-run.
- When a target repo's main clone is dirty or behind `origin`, the agent creates its own worktree (`git -C <main> fetch origin && git -C <main> worktree add -b <feat> <dir> origin/<base>`) and touches the main clone only through `fetch` and `worktree add`: no checkout, pull, stash or edit. The lead's own uncommitted work in that clone stays intact, and the agent's report names the worktree path. Give the worktree directory as an absolute path: a relative one in `git worktree add` created worktrees nested inside the clone, twice in one run; delete those and recreate them with the absolute path before any commit.
- For a remote feature branch that already exists, the agent's worktree tracks it: `git -C <main> worktree add <main>-wt-<sujet> origin/<branch>`, then inside it `git switch -C <branch> --track origin/<branch>`. Use `-b` only for a branch that does not exist on origin. Every worktree is created from a fresh `git fetch origin` of `origin/<branch>`, never from a local branch or a worktree left over from an earlier rebase, which may be stale.
- Before inserting a block into a file on an older base, check its line endings (`git -C <repo> show origin/<base>:<path> | file -`). A base whose file is CRLF gets the block in CRLF too, so the diff shows only the addition.
- When the user chooses to have the lead run writes that the classifier refused to subagents, the lead runs them itself, one repo at a time. After each push it re-reads that MR's head pipeline by `sha` before the next repo, and it does not relaunch the refused agent on the same write.
- A lot brief must not demand a render proof that is byte-identical across a chart version bump: `helm.sh/chart` and `checksum/config` change with the version, so the agent stops on its own correction. Write the admitted line patterns into the brief as exact `sed` filters, as helm-render-diff-check requires. On 21/10 the lead wrote "identique octet pour octet" into the lot 1 brief and had to send a correction to three lots.
- Every worktree a lot creates (including a detached `origin/<base>` worktree for a "before" render) is named in its hand-back with its absolute path. When the lot closes, the lead removes each one with `git worktree remove` only after `git -C <worktree> status --porcelain` prints nothing, then checks `git worktree list` in the main clone. A hand-back that leaves a worktree behind is not a closed lot.
- A worktree may have no git credentials, so its `git fetch` fails while the main clone's succeeds. The lot then fetches from the main clone (`git -C MAIN fetch origin`), reads the refs there, and names the failure in its report. It never rebases or pushes a branch whose fetch it could not complete.
- Each agent writes its full report to a file and replies with a status line only (DONE, DONE_WITH_CONCERNS, NEEDS_CONTEXT or BLOCKED), then commits, merge request URL and pipeline state.
- If an agent reports that its report file could not be written, it returns the full report inline in its final message. The lead copies that report into progress.md and never cites the missing file as a record.
- Before reporting that a set of repos "has" a shared file (a helper script, its tests, its lock), compare blob hashes per repo against the reference copy: `git -C <repo> show origin/<base>:<path> | sha1sum`, and read each hash next to the reference's. Counting files present hid a version split in the 21/10 run: 10 of 15 repos carried helm_diff.py, but on `bleu` 2NA had `037ce5d` while 1XM had `835b3ee`. The copy lot writes the same hashes after its copy and reads them back from origin.
- Before a lot copies a file from a sibling group, the lead keeps the reference copy in the workspace (`ref-<group>-<branch>/`, with the sha1 in the name of the brief) and the pilot's report lists each changed file by exact path, so every lot copies the same set.
- When the lead asks "pourquoi ce lot est en arrêt ?", answer from evidence before any restart: the agent's log timestamp, its last command, and the pipeline or MR state read through the API. A lot that is waiting on a bounded poll is still running; say so with the timestamp.
- Keep `progress.md` next to the briefs: pre-flight conflicts, one line per ruling (`Ruling: decision — why — cost if wrong`), and the dispatch list. Append on each hand-back.
- Before recording a hand-back, re-derive it from the base branch log (`git log origin/BASE..HEAD`) and the report files, as the verify-subagent-handback rules require.
- Reviewers run read-only and diff each branch against the plan's scope. Any change the plan did not ask for (for example a `securityContext` added "par cohérence" with other environments) is a finding, sent back for removal.
- Send each reviewer finding as a fix round to the same implementer via SendMessage, one finding per item, naming the file, the expected render result and the base commit. Re-review only the fix commit range (`git diff <previous-sha> <fix-sha>`), plus the render fingerprints of untouched environments.
- When an open MR by another author touches the files a lot must change, the lot does not wait for that MR to merge and does not integrate it. The user's ruling (21/10, api-core) was to migrate on the current base and have the other author rebase their MR afterwards. The brief says the other MR is neither merged nor touched. Apply this as the default to the same situation and ask only when the other MR changes the contract the migration relies on.
- A follow-up change to an MR that an implementer already opened goes to the same finished agent via SendMessage, which resumes it. Do not open a second MR for a one-commit addition.
- A user decision that changes a rule while agents are still running (for example a flow moved into the platform base): send one addendum via SendMessage to every running agent it touches, asking for one more commit on top (no amend, no force-push), and record the decision and the agents it reached in progress.md. Agents already finished are resumed the same way.
- When a removal in an application repo depends on a platform change, record the merge order in progress.md: the platform base must cover the same flow in every environment before the application rule is removed.
- A script that writes secrets gets a reviewer that is read-only and may run the script only in simulation mode. Any `--apply` run is left to the lead.
- Record each unresolved finding as a ruling line in `progress.md`, with the cost if the ruling is wrong. The lead decides the ruling; the implementer does not.
- Count fix rounds per task in `progress.md` as `fix round N/5`. At round five, stop dispatching and escalate the open findings to the user with a ruling request, instead of starting a sixth round. For a single document such as a runbook, one fix wave is followed by one scoped re-review of the changed sections; its residual findings go to the user as rulings, not to a second fix wave.
- Give each reviewer its own brief file with the plan's review-focus checks and a fixed answer format: a spec verdict (pass or fail), a quality verdict (approved or to fix), then findings ranked by severity. A reviewer that must mutate a file works only on a copy under a scratch directory outside the repository tree.
- Before a shared validation script or CI template is copied into a lot, have a read-only reviewer plant faults on the pilot's copy and confirm each check exits non-zero with its own message. A pilot that passes its own checks can still hide a check that never fails; harden the script on the pilot first.
- Once the pilot MR is merged, append an "Acquis du pilote" section to the shared brief: the reference files later lots read with `git show origin/BASE:<path>`, the decisions already settled and marked "do not re-discuss", and the pitfalls the pilot hit. Later lots inherit it instead of re-deriving it. A check added to the shared brief after the pilot merged goes to the pilot as a catch-up MR on the same base branch (new branch, new MR); the merged MR is not reopened.
- After each review round, append every finding that applies to all repositories to the shared brief as a numbered complement (`C1`, `C2`, ...), with the exact check or value and the fix. Lots not yet started and later fix rounds read the brief, so the same defect is not found twice.
- A validation script that a lot copies keeps its per-repo values (expected services, release prefix, chart directory, source ref) in variables at the top of the file. Never hardcode a feature branch name as the source ref: the branch is deleted after its MR merges, and then the script cannot run on that repo and its checks have to be replayed by hand. Each implementer reports which variable the next repo must change; a hardcoded list copied across repos silently checks the wrong thing.
- Before a lot pushes, check that its repo has a `.gitlab-ci.yml` with a rule that runs on merge requests (`glab api projects/<id>/repository/files/.gitlab-ci.yml?ref=<base>`, or the file listed in `git ls-tree origin/<base>`). A repo without one cannot be green: the lot stops as `bloqué-sans-ci`, unpushed, and the lead tells the user, as the global CLAUDE.md requires. Evidence: the 19/10 v4-b lot pushed keycloak and shell MRs whose `head_pipeline` was null and whose repos had no `.gitlab-ci.yml`.
- Open each MR right after the first push. CI jobs gated on "an MR exists" stay `manual` until then, so check the job list only after the MR is open before claiming validation ran.
- When a second wave of MRs in a repo depends on a first wave (for example extraIngresses on top of a helm-diff workflow), do not open the second wave's MRs until the first wave is merged. A branch cut from the unmerged first wave carries its commit into the second MR's diff. Prepare the second wave locally, check its render, and push only after the first wave's merge is read back from the target branch.
- Per-repo review approval does not prove the set works. After every lot is approved, run one whole-set pass that renders every release in every environment and checks contracts that cross repositories: each Service, secret, ConfigMap or host a chart references must be produced by some repo or by the platform base in the same namespace. In the 2NA run, each repo was approved on its own while `tenant-inventory-register-config` mounted `orange-internal-g2-server-ca`, a secret the converted Oathkeeper chart no longer created, so its pods would have stayed in `ContainerCreating`. Fix that as a fix round to the owning implementer, then re-run the whole-set pass.

- When the user asks for a final artifact listing every MR, the lead builds it only after each MR has been checked through the API. Re-read every head right before publishing and diff the new heads against the snapshot the earlier status used: a head that moved after a subagent's hand-back (a fix pushed by the same agent) makes the earlier table stale, and that row must be rewritten with the new sha and pipeline before the artifact is published. One row per MR: group, repo, MR link, target branch, head sha, head pipeline status and source, and the repo's status. A repo with no MR gets a row with its reason. Save it as a file the user can open, and link it from the final reply.

- When the user narrows the scope mid-run ("on va faire plus simple, seulement les dépôts de déploiement"), stop the running agents whose repos fall outside it (`TaskStop`) and re-derive the inventory for the remaining set before dispatching the next wave. Then close each out-of-scope MR with a note stating the reason, using `glab api -X PUT projects/<id>/merge_requests/<iid> -f state_event=close`, and delete its remote feature branch. Remove the local worktree only after `git -C <worktree> status --porcelain` prints nothing. Record each closure and removal in progress.md. Evidence: the 19/10 run closed six MRs and removed eight worktrees after the user narrowed the scope.

- A brief that migrates a documentation file (README) from the pilot says "migrate the whole file, read it end to end, do not limit yourself to the touched lines", and the reviewer reads the whole file too. A review that passed a lot as Approved on touched lines missed a README still describing removed schema, docs and hook files, and a corrupted table row; the complement that fixed it was added after the lot had started.
- When a lot reaches a gap in the shared chart's contract (a missing value, a feature the chart does not expose), the lot stops as BLOCKED and does not pick a local workaround. The lead lists the options (local template, a new chart tag, or leaving the object out of scope), each with its cost, and the user rules. Prod image choices stay with the user as well.
- Do not dispatch a reviewer on a repo while another agent can still push to it. If a placeholder or fix agent may commit to the same MR, pin the expected head sha in the reviewer's brief and re-read the MR head before recording a verdict. The 20/10 run reviewed api-iam-doc !22 while a placeholder agent was adding commit cd1f713 to the same branch, and the review had to be redone against the real head.
- An agent stopped by the user or by TaskStop cannot be resumed: SendMessage returns "was stopped by the user and was not resumed". Relaunch a new Agent with the same brief file and fresh scratch names, tell the user it was relaunched, and treat the stopped agent's partial output as cancelled.

- When the permission classifier refuses a call that mixes a write with other steps (a description update sent with a push, a title change sent with a merge), the agent splits it into one call per write, re-reads between them, and reports what passed. A "transient" classifier error gets one retry as a separate call; a refusal that persists is reported, never routed around. On 21/10 two description updates were refused in one lot and passed when sent alone.
- A bulk check whose output is truncated for some repositories leaves those repositories unverified until each one is re-run on its own. Never count a truncated listing as zero findings.

- Build the repo list of a status sweep from the group's project API, paginated and count-checked: `glab api --paginate "groups/c-iam-integration%2Fdeployments/projects?per_page=100"` (substitute the group path), then compare the count with the group's own total. A list typed by hand covers only the repos the lead remembers; a sweep over seven hand-typed repos said nothing about the other charts of the group, and the user had to ask whether the set was complete.
- A lot brief must carry the full repository list of that lot, copied from the inventory, not a summary of it. A lot brief that named fewer repos than the lead meant made the agent create nothing; the lead re-sent the list by SendMessage. Before dispatch, count the repos in the brief against the inventory; after hand-back, count the MRs and the repos reported against the same list, and re-dispatch any missing repo to the same agent instead of accepting the lot as complete.
- Before each Agent call, scan the brief for unfilled tokens (`PLACEHOLDER`, `<repo>`, `TODO`, `LISTE`, any upper-case word standing where a list belongs, an empty list under a "Dépôts" heading) and count its repos against the inventory. Check the last lines of the brief first, since a list left as the final word slips past a scan for the usual tokens. A brief with an unfilled list makes the agent stop with nothing done, so a second dispatch costs a round trip. Build the repo list in the same step that writes the brief, never in a later edit. A brief sent with the literal `REPOS_PLACEHOLDER` made the agent stop with no output, and the lot had to be re-sent by SendMessage.
- An agent does not inherit the lead's target. Each brief gives the absolute worktree path and starts with a `cd` into it; each `glab` call addresses the project by `projects/<id>`, not by `-R`. On 21/10 a lot ran in the lead's cwd (another repo) and its MR create targeted that repo, which is why the report had a 422 and a wrong-repo attempt. The lead checks the MR's `web_url` project after each hand-back.
