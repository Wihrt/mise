---
name: helm-render-diff-check
description: Use when verifying what Helm renders per environment, proving a chart change is strictly additive or backward compatible, or posting a Helm diff as merge request notes.
category: verification
---

Prove a chart change by rendering every environment before and after, comparing parsed documents, and listing what disappeared and what appeared. A lint pass is not a render proof.

- Render each environment with the repo's own command (find it in mise.toml or CI), on the previous head and on the branch. Write the renders outside the repository.
- Count the environments from the repo's own `environments/*.yaml` (or the render script's list) before writing "N environnements" or putting N in a brief. A brief that says 6 environments for a repo that has 4 (ui-iam-doc: develop, int, qa, prod) makes the agent either fail or report a count it did not render; the agent's "identique sur ses 4 envs" was only caught because the lead re-counted.
- The release name is the GitOps one, `application-environment` (see `RELEASE_PREFIX` in mise.toml and the render script), not the repository name. A brief that assumes the repository name renders the wrong objects; read the script before rendering.
- A default in the render script (for example `RELEASE_PREFIX` in `tests/render.sh`) is not a confirmation of the release name. Before a repo's `[env]` value is reported as established, read the HelmRelease name the GitOps repo (flux-cd) applies for that repo; until then say "non confirmé côté flux-cd".
- Compare parsed YAML documents keyed by kind, namespace and name, never raw text. Report each object that disappeared; any object that appeared must be intended. Before explaining what a disappeared Service served, list every Service of the base render with its selector and the pods it matches; a user asking "is it the one PostgreSQL points at?" needs that table, not a guess from the name.
- Run `kubeconform -strict -summary` on each render that holds a CiliumNetworkPolicy. Pass only with Invalid 0 and Skipped 0.
- List the rules of each render with `python3 -I scripts/policy-rules.py FILE` to read which peers and ports remain.
- To test a new value, use a temporary values file outside the repository and show the rendered object. Never commit it.
- Normalisation can hide the change under test. Sorting keys and lists turns a moved initContainer or env var into "identical"; stripping `Chart.yaml` hides the `helm.sh/chart` and `app.kubernetes.io/version` labels of a renamed chart; a separator change in an annotation value is still a diff. A `helm.sh/chart` or `app.kubernetes.io/version` label that changes because a chart is consumed under a new dependency alias is a real difference, not an admissible "metadata label" difference: a subagent classified it as admissible and the user rejected it. Name it in the report and get a ruling before writing "identique". Keep order-only and metadata differences in the report, list every field the normaliser removed, and read the raw diff file before writing "identique". A bare key (`replicas:` with no value) renders null and Helm drops it, so the key disappears from the render: that is a difference, not an equivalence, and it goes to the user's ruling. Do not record it as admitted in progress.md on the lead's own judgement, even when the Kubernetes behaviour is the same. The same holds for the relay to the user: list each out-of-list object with its before and after lines and ask for the ruling. Phrases such as "ne change pas le comportement" or "les objets sont recréés" are a verdict the lead has not established, so they are left out until a ruling or a read-back proves them. A comparison script that classifies a JSON string embedded in a ConfigMap as YAML-equal (`TEXTE-YAML-EGAL`) hides changes inside that string: compare the string byte for byte before writing "identique".
- Render the way the GitOps controller renders: the chart's own `chart/values.yaml` first, then the environment file. Never render with an empty or environment-only values file, because a key the templates read from the chart defaults (such as `global.selfSignedIssuer`) is then absent and the test passes while the real render fails. Write the failing render test first, then fix. For each environment, compare the `global` keys of `chart/values.yaml` with the keys of that environment's `environments/values.yaml`; a key missing from one environment file changes only that environment's objects.
- `helm-diff local CHART1 CHART2` applies the same `-f` values to both sides, so a change inside an environment values file shows 0 changed lines. Before trusting it, merge the values per side into a copy of the chart, then run `helm-diff local` without `-f`. The merge should follow Helm's semantics (maps merged recursively, lists and scalars replaced, a `null` in a later file deletes the key), ideally in a Python script (see python-script-under-uv); the `yq ea '. as $i ireduce ({}; . * $i)'` form is the shell fallback. Gate the merge with a self-check: each side's render of the merged copy must equal `helm template ... --values ... --values ...` for that environment, or the environment is reported as failed. Check the count against `diff -u` of two `helm template ... --values ... --values ...` renders; they must agree. A `null` in the chart's own `values.yaml` default is also removed from the merged values, so a merged-copy render can differ from the `-f` render for that key: the self-check then fails, which is the intended catch. Fix it in the chart (drop the null key or give it a value), then rerun the self-check; do not report the environment as equal.
- Install `helm-diff` through mise as a standalone binary. It is not a helm plugin: `helm diff` answers "unknown command", so call `helm-diff local <base> <head> --release <r> --namespace <ns> --no-color`.
- A chart version bump is never byte-identical, even with unchanged templates: `helm.sh/chart: <name>-<version>` changes on every object, and `checksum/config` changes wherever a ConfigMap carries that label. Write the admitted lines into the brief as exact patterns, filter only those with one named `sed` before `cmp`, and list each removed line with its before and after value. Never write "octet pour octet" or "identique" for a version change; a proof taken at one chart version does not cover another.
- Hash each untouched environment's render before and after a change; the hashes must match. Render from a clean extract (`git archive <ref> | tar -x -C "$(mktemp -d)"`, then `helm dependency build`), never inside a worktree another agent may edit.
- Before a first install into a namespace that already holds same-named objects (ServiceAccount, Secret, NetworkPolicy), list them with `kubectl get <kind> -n <ns> --show-labels` and check for `meta.helm.sh/release-name`. Decide adopt or delete per object and record the decision.
- Publish a render diff as one MR note per environment, each with its own hidden marker (`<!-- helm-diff:<env> -->`). List the MR notes once, all pages, and match them by marker.
- The publisher overwrites each environment's note in place. Before pushing a new head that re-runs helm-diff, save the current notes of the MR to a scratch file outside the repository (GET the notes API, all pages). Afterwards, compare the saved notes with the new ones. Without the snapshot, the old render can no longer be read back, and the before/after claim rests on a regeneration, not on what was published.
- Create or update an environment's note when its render changed, failed, or the environment was added or removed. When it turns unchanged, update its existing note to say so, so no stale diff stays. When it is unchanged and has no note, create nothing and log one line for it.
- The `helm-diff` CI job posts notes only in a merge request pipeline; check the pipeline `source` is `merge_request_event` first (`gitlab-ci-mr-pipeline-source`).
- A green `helm-diff` job with no changed render posts no note. A job status of `success` does not show what it published: read the job trace for the "aucun changement" line, or list the MR notes by marker, before writing "aucune note publiée" as a fact. Until then it is an inference.
- The `helm-diff` note publisher does not redact values: a rendered or changed line with a secret in clear lands in the MR note. Before the first push, run `git diff origin/bleu..HEAD | grep -E '^\+' | grep -ciE 'apikey|password|token|secret|dsn'` and read each hit. A change that adds a secret to a note is held out of that MR: ship the rest alone and report the held line with the decision it needs.
- The publish token variable name is not portable. Never assume the name another product's script reads. List the group's and project's CI/CD variables by key only (`glab api groups/<group>/variables`, print `key`, `masked`, `protected`), and find the one that holds a valid token. Keep the script byte-identical to its source and map the name inside the job's script, not in `variables:`: the first script line is `export READ_NAME="${VALID_NAME:-}"`, preceded by an `if [ -z "${VALID_NAME:-}" ]` check that prints only the variable's name. On a group where the generic name `GROUP_TOKEN` answers `401 invalid_token` and `GITLAB_GROUP_TOKEN` is valid, map `GITLAB_GROUP_TOKEN`. A `variables:` reference (`READ_NAME: $VALID_NAME`) left the token unresolved in a job whose notes read got a 401; the same job passed once the copy moved into the shell. A 401 on the note request means the value is stale, or the wrong variable is mapped, so check the other existing token variables before reporting. Never read or print a value, its length or its prefix; a probe of a token's shape was refused by the session's safety check, so report the 401 and ask the user to check the token's expiry and its `api` scope.
- A values change is not done until the repo's generated files are regenerated by its own mise task (the values schema and the chart's HELM doc), and their output is committed with it. A pre-commit schema hook refuses the commit otherwise, and the branch is then pushed without the change.
- A non-blocking `helm-diff` job on a chart whose dependencies come from a remote Helm repo (for example `ory`) fails at the repo root until the job adds that repo and runs `helm dependency build` first. A green pipeline can hide that red job: read the job's own status and its trace line for each environment.
- A `helm-diff` job whose chart pulls a dependency from a private OCI registry (for example `shared-chart` on `registry.example.com`) fails with `403 denied` at `helm dependency build` unless its script logs in first, after `mise install`: `echo "$CI_JOB_TOKEN" | mise exec helm -- helm registry login registry.example.com --username gitlab-ci-token --password-stdin`. A job that only extends `.mise` opens no registry session, and lint or render jobs may pass while it fails. The consuming project must also be on the registry owner's job-token allowlist. Copy the line from a branch whose helm-diff already passes; a branch migrated before its helm-diff job was added lacks it, and the 403 shows only in that job's trace.
- When the helm-diff self-check fails, the job publishes its notes with status `failed` and no diff. Any per-environment difference a lot then computes by hand is not a published render: report it as unpublished, and name the environments that were not rendered (a lot that compared two environments did not prove the other four).
- A merge request that changes no render proves only the read path (notes GET, "inchangé" lines). To prove the publish path, push a commit that changes one rendered environment, then read the note bodies back through the notes API and check the marker.
- Prove the diff tool on a positive case before trusting its "inchangé" lines: change one value in one environment's file, expect "rendu modifié" for that environment only and "inchangé" for the rest, paste the diff, then restore with `git checkout -- <file>`. Pick a value the render prints. Read every environment's line in the positive run, untruncated: a `head`-cut report hid two environments, which then stayed unverified. A key the chart's template never prints (such as `replicaCount` when the Deployment omits replicas) gives a false "inchangé"; use an image tag or a pod annotation instead.
- Publish every environment before exiting non-zero for a failed render.
- A claim of the form "only X disappears" or "only X changes" is checked against the list of removed and added `kind name` pairs, never against the diff's line count. Removing a feature switch also removes every object the chart gates on it: an Ingress switch dropped its Middleware and Traefik NetworkPolicy objects in keto (21/10, 143 deleted lines, 0 added). Name each such object in the MR note and the relay, and say whether it is intended.
- For a withdrawal (an application set to `enabled: false` in one environment), the expected render diff is exactly that application's `GitRepository` and `HelmRelease` in that environment. Any other removed or added object is a finding, and the other environments must hash identical.
- When the user requires a chart change to be strictly additive, on every branch it reaches (including legacy branches that are about to die), prove it per environment file listed by `git ls-tree -r --name-only origin/<base> chart`, never from memory. (a) Default values: base and branch renders from `git archive` extracts must have equal sha256. (b) With the change's example values file added to both sides: split each render on `---`, compare as sets keyed by kind and name; the branch set must equal the base set plus exactly the added objects, and every other document must be byte-equal. A helper change that reorders annotations still shows as a difference; list it. (c) A required value left unset must fail the render with its message. Remove the whole key that holds the required field (for example the entry's `certificate` map), not only the leaf: a leftover `certificate: null` makes the template fail on a nil lookup (`dig`) with a different error, so the check passes for the wrong reason. Assert the chart's own message in stderr and a non-zero exit code. Pass the comparison base as a bare branch name (`dev`, `azure`): a comparison script that prefixes `origin/` itself fails on `origin/origin/azure` with `fatal: not a valid object name`.
- When a `mise.toml` variable is renamed (for example `RELEASE_PREFIX` to `RELEASE_NAME`), grep every repo for its readers, including the defaults in `tests/render.sh`: `grep -rn 'OLD_VAR' .` on each clone and on `origin/<base>`. A script that still reads the old name falls back silently to its own default (`release="${RELEASE_NAME:-api-authz}"` in one repo, `release_prefix="${RELEASE_PREFIX:-dgs-job-config}"` in another), so the render passes while the variable no longer drives it. Name each such reader in the MR and decide whether to rename it in the same change or leave it for a later one.
- To prove a file is byte-identical to a pilot's copy, compare blob hashes of the two refs, not renders: `git show <pilot-ref>:<path> | git hash-object --stdin` against `git show origin/<branch>:<path> | git hash-object --stdin`. Equal hashes is the proof; a cheap check that needs no extract.
- Every behaviour a change claims (an explicit annotation overrides a derived one, a duplicate key is refused, a removed key is rejected by the schema) needs its own case in the check script, with the rendered line or the refusal message as output. Before the check runs, say which claim it does not yet exercise; do not report the claim as proven.
- Keep the commands and their output as evidence. A count without the command that produced it is not a check.
- A repeated top-level key in a values file (a second `iamB2B:` block under the same environment) raises no error: the parser keeps the later block and the earlier URL disappears from the render silently. Put the keys of one map in a single block, and read the rendered value of each changed key against the base render to catch it. The 21/10 rebase hit this; only the render exposed it.
- When a chart changes the default of an optional field (for example the issuer of an extra entry with no `certificate.issuer`), render each branch with one temporary values file holding two entries: one without the field and one with it set. Parse the documents and print, per entry, the annotation its Ingress carries, and the Issuer kinds present (a removed self-signed Issuer must be absent). If `helm template` fails on a missing dependency, run `helm dependency build` in the extract and render again; if it still fails, report its first error line.
- Any cherry-pick, conflict resolution, rebase, or `git checkout <base> -- chart` restore on a branch voids the earlier render proof: rerun the sha256 and additive checks on the new head before writing "rendu identique" anywhere. A cherry-picked lint fix that edits the main Ingress (for example an alias moved behind `tpl`) breaks "every other document byte-equal" even though it fixes the pipeline; ask the user for a ruling before pushing that fix.
- Before restoring a chart to base to make a proof trivially equal, list the branch's own commits that touch `chart/` (`git log --oneline origin/<base>..origin/<branch> -- chart`). Restoring drops lint fixes already pushed and turns the pipeline red; reapply each one with `cherry-pick -x`, then recheck the pipeline by `sha`.
- When the base itself fails to render, a comparison cannot prove additivity. Report that file as a documented exception with the base's error line, and prove that the branch renders. Never report such a file as "identique" to the base.
- To learn which hosts an Ingress really carries on each branch and environment, render; do not grep values files. For each branch, extract with `git archive origin/BRANCH | tar -x -C` a fresh directory, run `helm dependency build`, then `helm template RELEASE CHART -n NAMESPACE -f ENV.yaml` for each environment file, and read `spec.rules[].host` from the Ingress documents. Before adding an extraIngress host, confirm the same host is not already on the main Ingress of that branch and environment, or it is served twice. A Chart.yaml that names a repo alias such as `@ory` may be rewritten to its URL inside the extract only, never in the repository.
- When a values change copies one environment's block into another (a dev ingress pasted into int or staging), list every object the render adds that is reachable from outside the cluster: Ingress, IngressRoute, Middleware, LoadBalancer Service. An exposed object in an environment where it was not intended is a finding even when the rest of the diff is additive. Check whether anything in front authenticates it; an admin or write API with no authentication layer is a blocker, not a note.
- When the user says the change cannot be deployed or checked on a cluster, the render diff against the base is the only proof. Do not propose kubectl reads as the next verification step; name each fact the render cannot show (a proxy redirect, a consumer outside the grepped repositories) as unverified in the MR description.
- Before writing which objects a change recreates, list `kind name` for every document of each environment's render on the base and on the branch (`grep -E '^kind:|^  name:'` on the parsed output). A chart can render only ConfigMap, Job and CronJob, with no Deployment or Service; a claim of recreated Deployment and Service written from the chart's intent was wrong and had to be corrected after the lot's render.
- A check of references between objects across several repositories' renders (a Secret, ConfigMap or Service named by one object and produced by another) is a separate proof from the render diff. Use helm-cross-repo-reference-audit, and run its positive control before trusting zero unresolved.
