---
name: readonly-cluster-and-secret-inspection
description: Use when inspecting kubectl or Vault state read-only, or before any kubectl apply, bootstrap, delete or Vault kv write on a cluster.
category: security
---

Inspect live state with read verbs only, name the context and namespace on every call, and never print a secret value.

- Cluster: use `kubectl get`, `kubectl api-resources` and `kubectl auth can-i` only. Writes (`apply`, `create`, `patch`, `label`, `annotate`, `delete`, `helm upgrade|uninstall`, `flux` reconcile) are out of scope unless the user asks for that exact step.
- The hook `cluster-guard` (`harness hook cluster-guard`) asks the user before each write of `kubectl`, `helm`, `flux`, `argocd app`, and `tofu`/`terraform` (`apply`, `destroy`, `import`, `taint`, `state rm|mv|push`); reads, dry runs and writes on a `kind-*` context pass. Never rephrase a command to get past it (a script, `xargs`, a subshell).
- A go covers one step, on one environment, in the message that asks for it. A goal ("carré jusqu'en preprod"), a go given for another topic (Vault readiness), or a yes earlier in the session does not cover a bootstrap, apply, delete or Vault write now. Ask in the current message, naming the environment and the action. Never pipe `o` or `yes` into a script's confirmation prompt (`[o/N]`): the prompt is the user's gate. A "stop" from the user halts every write step at once; report what already changed.
- Pass `--context <ctx> -n <ns>` on every command so a default context never receives the call.
- `kubectl auth can-i VERB RESOURCE --as=system:serviceaccount:NS:SA` needs the impersonate verb. When it is refused ("is not allowed to impersonate user"), it gives no verdict on the ServiceAccount: read its RoleBindings with `get rolebindings`, or report the permission as unverified. A "server doesn't have a resource type" warning printed beside that refusal is not evidence that the CRD is missing.
- `auth can-i` answers for the caller only. Before saying that the user can perform an action (for example create a Job by hand), run `auth can-i` for that exact verb and resource in that namespace, and quote the answer.
- On clusters behind a corporate proxy, export `NO_PROXY` and `no_proxy` with the cluster's proxy exclusions in the same Bash call as `kubectl`; take them from the user's existing environment or kubeconfig/proxy config, never hardcode a domain. The list of policies came back only with it set.
- To confirm an in-cluster Service name before a chart uses it, list that namespace's Services in the same call: `NO_PROXY=<cluster proxy exclusions> kubectl --context <ctx> --request-timeout=25s -n <ns> get svc -o name`. The printed names are the evidence. A `Forbidden` on another namespace is recorded as unverified; do not switch context or credentials to read it.
- Never use `-o yaml` or `-o json` on Secret objects. Read names, types, labels and annotations with `-o custom-columns` or `jq` on `.metadata`.
- Vault: `vault kv list` for paths; `vault kv get -format=json <path> | jq '.data.data | keys'` for field names. Report field names only, never values.
- GitLab CI/CD variables: `glab api groups/<group>/variables` (or the project's `variables`) through `jq '.[] | {key, masked, protected, environment_scope}'`. Report key names and flags; a value is never printed, copied into a file, or read back into a brief. The endpoint returns every value, masked ones included, so the `glab api` call and the `jq` filter must sit in one pipeline in one command; a bare call, or a delegated reviewer's own call without the filter, prints the values into the transcript. If that happens, name the key and the call in the report, tell the user to rotate the variable, and never repeat the value.
- If a read is refused (Forbidden, expired token), do not work around it or retry with other credentials. Record the refusal and continue with what is readable.
- When a read of a cluster-scoped resource (a CRD such as `pushsecrets.external-secrets.io`) is Forbidden, do not take the API version from web search or docs. Ask the user to run `kubectl api-resources --context <ctx> | grep <kind>` and paste the line; write the `apiVersion` only from that pasted output.
- A delegated read-only reviewer gets its allowed namespaces and read verbs written into its brief. Cluster-scoped reads (`get clusterrole`, `get ... -A`, anything in a system namespace such as `flux-system`) fall outside that grant even when they only read; the call is not made, and any attempt that already happened is reported as a deviation.
- In a read-only audit pipeline that counts matches, `grep -c` exits 1 when the count is 0, which marks a valid call as failed. Append `|| true` after such a count so a zero is reported as a result, not an error.
- Count HTTP errors in JSON logs by parsing the status field (`jq -R 'fromjson? | select(.http_response!=null) | .http_response.status'`), never by grepping for `502|503`. Those digits match ports, timestamps and UUIDs. A grep for them reported 2 to 6 "network errors" per pod that were all false positives, and only reading the matched lines showed it. Every HTTP status in the sample was 200.
- To check that a live Secret matches another source (a Vault entry or a ConfigMap), hash each side in a pipe with `sha256sum` and print only the first 12 hex characters of each digest; report "equal" or "differs". Never print both values or diff them on screen.
- A credential found in clear in a ConfigMap, a values file or a URL (an `apiKey=` query parameter, a DSN) is a finding: report the file, the key and the commit, never the value. The redaction filter must sit in the same command as the first read of that file (`git show`, `cat`, `sed -n`, `grep`); a read that ran before its filter has already printed the value. If that happens, say so, name the call, and ask the user whether to rotate the key. Filter any `git grep` or `git diff` output that may carry it with `sed -E 's/(apiKey|password|token)=[^ "&]*/\1=REDACTED/'` before it reaches the transcript.
- To audit a Vault folder for unfilled entries, run `jq` on `.data.data` per entry and print only the field names whose value is empty or equals the placeholder token `A_RENSEIGNER`, plus the entry's version. Names and counts only; never the values.
- A read is a snapshot of its own moment. After a write or delete, re-read once the reconciliation has settled (wait at least one Flux interval), and quote the `date` with the counts. Never say "nothing is left" or "everything is still there" from a read taken during or before the operation; re-read first, then state the result with its time.
- Triage a workload that does not start, in this order: the namespace `ResourceQuota` (kind ResourceQuota), then the pod's events (`events_list` with `fieldSelector=involvedObject.name=<pod>`), then each Secret or ConfigMap the event names (check it by name with `-o custom-columns`, never `-o yaml`), and the HelmRelease `status.conditions` last. `CreateContainerConfigError` and `FailedCreate` point at the first two.
- A saturated quota makes pods fail to create with `FailedCreate` events. Freeing it does not revive a HelmRelease already `Stalled` with `RetriesExceeded`: its status stays frozen until a reconcile, which is a write that needs the user's go.
- Logs of a pod that a newer release replaced are gone (`pods_log` answers `not found`). Read logs only from pods listed in the current read.
- An empty MCP result (`completed with no output`) is not proof of absence: re-query with the kind or label the object actually carries before saying it does not exist.
- To find out why a database a workload depends on is down, probe it from an existing in-cluster client pod that is already deployed (for example `kubectl --context <ctx> -n <ns> --request-timeout=25s exec deploy/psql-client -- sh -c 'PGCONNECT_TIMEOUT=5 psql -tAc "select 1"'`), with `NO_PROXY` exported in the same call. Read the error, do not guess the cause: `Connection refused` means the host answers and refuses the port; a timeout means a network policy drops the traffic; `the database system is in recovery mode` means a managed server is restarting, often after a tier change. Only a `select` goes through the probe; never a DDL or a write.
- A "network policy" explanation for a database failure is a hypothesis until the error message separates it from a refusal or a restart. Name the message you read, and say what you could not verify (for example the cloud console) instead of attributing the cause.
